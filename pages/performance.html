Why is there no live demo here?

This site is published as static files on GitHub Pages. A load test needs a server that can be slow, fail or run out of capacity on request, and the ?delay and ?fail toggles used elsewhere on this site are simulated inside the browser, where k6 cannot see them. So the lab comes with a tiny practice server that runs on your own machine.

Never point a load test at a site you do not own. That includes this site's GitHub Pages address. The k6 scripts in the repository refuse to run against anything but localhost.

Get started

  1. Install k6 (version 1.0 or newer): winget install GrafanaLabs.k6 on Windows, brew install k6 on macOS.
  2. Clone the repository and run npm install.
  3. Run npm run perf:smoke. It starts the practice server, runs a first k6 script and stops the server again.
  4. Run npm run perf:load, then npm run perf:stress and compare the results.
  5. Work through the exercises below. To explore the API by hand, run npm run perf:server and open http://127.0.0.1:4180/pages/performance-api.html.

k6 exercises

Six exercises with starter scripts and worked solutions live in the repository under perf/k6/exercises, described in perf/EXERCISES.md.

  1. Thresholds: give one endpoint its own limit, using tags.
  2. Configuration: settings from the command line, and a ramp-up.
  3. Test data and correlation: one account per virtual user, a token passed between requests.
  4. Custom metrics: measure the business flow, not just requests.
  5. Open versus closed models: why 20 patient users are not the same as 15 new visitors per second.
  6. Resilience: honour 429 and Retry-After, retry a flaky service.

Vocabulary

Virtual user (VU)
One simulated user running your script in a loop.
Iteration
One run of the script's main function.
Check
An assertion that is counted but does not stop the test.
Threshold
A pass/fail rule on a metric, for example "95% of requests under 500 ms". It decides the exit code.
Percentile (p95)
95% of requests were faster than this value. Averages hide the slow ones, percentiles do not.
Throughput
How many requests (or iterations) are completed per second.
Think time
The pause a real user takes between actions. Without it the load is unrealistically harsh.
Closed model
A fixed number of users; each waits for its answer before the next request. It slows down together with the server.
Open model
New requests arrive at a fixed rate no matter how slow the server is, like real visitors.
Saturation
The point where a resource is fully used and requests start to queue: latency climbs steeply.

Exercises

  1. Assert the status badge when the API is not reachable, and that the hint explains how to start it.
  2. Mock /api/health with page.route to switch the badge to "online".
  3. Make the health check fail (500, then an aborted request) and assert the badge stays "offline".
  4. Use ?api= with a non-local address and assert it is rejected.
  5. Click "Check again" after changing the mock, without reloading the page.
  6. Assert the setup steps and the table of scripts by role, not by test id.
